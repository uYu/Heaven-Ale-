# 全程跨回合 MCTS 验证

## 算法与冻结版本

`src/game/ai.mcts.ts` 从第一轮开始搜索，不限于残局。每条树边是一段完整行动计划，包括移动、购买、出售、棚屋、特权等后续选择。执行后模拟其他玩家，轮到自己时继续展开下一层；未展开的尾部用启发式策略模拟到终局。

选择阶段使用 UCB：平均终局收益、探索项以及逐渐衰减的启发式先验。终局收益兼顾自己的分数与相对最强对手的分差。完成模拟后将结果回传到经过的所有树边，最终选择访问次数最多的根分支，同次数时比较平均收益。未完成模拟不回传，不能凭不完整结果取代已验证方案。

默认总预算为 36000 次规则执行，候选生成、树内行动、对手行动和尾部模拟都计入。根节点最多 36 个方案，内部节点最多 12 个。公开状态用于节点合并和行动计划缓存，真实种子、历史和隐藏牌序被剥离；未知牌从公开信息重建。每条根分支按自己的访问次数轮换相同四个牌堆/对手场景，对手模型为基线或普通。它仍是有候选裁剪、有限预算、近似对手模型的搜索，不是对所有合法策略的精确求解。

## 开发对照（不计入独立验证胜率）

种子 15000，轮换四个座位，一位候选、一位修改前默认困难、两位普通。全程 MCTS 为 4 胜 0 负，均分 38.25，对照 20.00，平均领先 18.25；保留旧开局、第三轮起使用 MCTS 为 3 胜 1 负，平均领先 15.25。因此选择全程版本做独立验证。

原始记录：`ai-mcts-dev-full.txt`、`ai-mcts-dev-hybrid.txt`。全程版本该批平均决策 837 ms，对照 348 ms；包含缓存动作，完整搜索通常需要数秒。

## 独立验证协议

预先选择新种子 16000–16003，每个种子轮换四个座位，共 16 局。一位全程 MCTS、一位修改前默认困难相对而坐，其余两位普通。对照是前两轮 `hard-v1`，第三轮开始旧 `ai.search.ts` 规划器，禁用此前的残局实验。不是普通 AI，也不是全程 `search-v2`。

验证中不修改候选策略或调参。最初进程在对话中断后停止，每个种子的座位 0 已完成并落盘；恢复时仅运行座位 1–3，不重复计算最初四局。

完整复现：

```sh
node --experimental-strip-types scripts/benchmark-ai.ts 4 16000 mcts hard-before-endgame normal
```

本次恢复命令（分别对四个种子执行）：

```sh
node --experimental-strip-types scripts/benchmark-ai.ts 1 16000 mcts hard-before-endgame normal 1
```

原始记录为 `ai-mcts-validation-16000.txt` 至 `ai-mcts-validation-16003.txt`，以及对应的 `-remaining.txt` 文件。每步检查状态不变量，超出 1500 个正式动作判为失败。得分胜率只比较新旧困难，平局按半胜；四人局夺冠率另算，并列分摊。

耗时统计只覆盖恢复后的 12 局，最初 4 局进程结束前没有保存耗时汇总。四个验证进程并行运行，CPU 竞争会影响墙钟延迟，不能直接与开发批次的毫秒数比较。

## 自动验证

新增测试检查第一轮和第三轮都能展开后续自己的行动、确定性、隐藏信息独立性、冻结输入不被修改、统一预算、计划缓存及失效处理、完整混合对局的合法性与终止。接入默认策略前共 48 项测试通过。

## 独立验证结果与启用决定

16 局全部完成，5619 次正式行动全部通过不变量检查。开发样本没有混入结果。

| 指标 | 全程 MCTS | 修改前困难 |
| --- | ---: | ---: |
| 双方比分胜负 | 14 胜、0 平、2 负 | 2 胜、0 平、14 负 |
| 双方得分胜率 | 87.5% | 12.5% |
| 平均分 | 40.4375 | 22.125 |
| 平均领先对方 | 18.3125 | -18.3125 |
| 四人局夺冠率 | 87.5% | 12.5% |

四个种子的得分胜率依次为 75%、100%、100%、75%。这支持当前候选比修改前困难更强，但只有四个独立种子，不能宣称长期稳定达到 87.5%。

恢复后的 12 局，按决策次数加权的平均耗时为新版 1066.52 ms、旧版 436.71 ms，约 2.44 倍。四个批次的新版 P95 为 4021–4112 ms，旧版为 1253–1817 ms；新版最大 4799.68 ms。计时包含快速缓存动作和四进程 CPU 竞争，不等于每次完整搜索耗时，也不代表单独浏览器运行的保证延迟。

因此将经过这批验证的同一 `createTreeAgent()` 接到默认 `hard`，从第一轮启用；`hard-v2` 保留修改前的分阶段策略。没有在验证后更改搜索参数或算法，冻结文件哈希仍匹配。新增路由测试检查默认困难在第一轮和第三轮均与已验证算法一致。

接入后完整测试 49 项全部通过，TypeScript 检查和 Vite 生产构建通过。

机器可读汇总为 `ai-mcts-summary.json`，生成命令如下。脚本拒绝缺失或重复的种子/座位，计时仅汇总实际保存的 12 局：

```sh
node --experimental-strip-types scripts/summarize-mcts.ts > docs/ai-mcts-summary.json
```

## 内存测量

使用 `scripts/benchmark-ai-memory.ts`，在 Node v24.19.0 / macOS 下分别用独立进程测试种子 71、16000、16003 的第 1、3、6 轮，共 9 个公开局面，默认预算 36000。输入局面由基线对局产生，不是内存最坏情况证明，也不是浏览器页面/Worker 的直接测量。

脚本在临时副本插入内存采样，生产搜索源码不变；约每 128 次规则执行计数采样一次，并在搜索返回前采样。短时间的堆尖峰可能漏采，RSS 另记录操作系统提供的进程最高水位。结果在 `ai-mcts-memory.json`。

| 指标 | 9 个样本的范围 |
| --- | ---: |
| 搜索前 JS 堆（主动 GC 后） | 8.48–8.99 MiB |
| 搜索中采样 JS 堆峰值 | 32.37–45.36 MiB |
| 相对搜索前的采样堆增量 | 23.88–36.45 MiB |
| 返回并主动 GC 后的 JS 堆 | 9.62–9.77 MiB |
| 整个 Node 进程的 RSS 最高水位 | 149.13–200.63 MiB |
| 搜索表中保留的状态节点 | 43–136 |
| 保留的行动分支 | 528–1257 |

36000 是规则执行预算，不是同时存储 36000 个完整棋盘。搜索表保存公开状态键和方案统计，每次搜索结束后可释放；计划缓存另保留接下来的行动和匹配键。应用使用一个 Worker 依次处理三位对手，不会为三位对手同时运行三棵搜索树。RSS 包含 Node/V8、模块、JIT、垃圾回收器保留页等，不能当作纯算法内存；GC 后 RSS 也不一定立即下降。浏览器的具体进程占用应单独测量。

```sh
node --experimental-strip-types scripts/benchmark-ai-memory.ts > docs/ai-mcts-memory.json
```
